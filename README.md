# kit-frontend

Next.js 16 + Apollo. Ходит в бэкенд **только через свой серверный слой** —
браузер адреса бэкенда не знает.

## Старт

```bash
pnpm install
cp .env.local.example .env.local     # и подставь адрес бэкенда и секрет
pnpm dev                             # :3800
```

Бэкенд должен быть поднят (`kit-backend`, `pnpm local` на :9800).

## Топология: почему браузер не ходит в бэкенд

```
Браузер ──► /api/graphql (этот же Next) ──приватная сеть + service-token──► NestJS
```

Что это даёт:

- **адреса бэкенда нет ни в бандле, ни в публичном DNS.** Его нельзя «пощупать»
  напрямую: наружу он не выставлен вовсе;
- **identity ставит сервер.** `X-User-Id` берётся из httpOnly-куки, браузер
  такое подделать не может;
- **CORS не нужен** — запрос same-origin;
- **токенов в localStorage нет.** Их читает любой скрипт на странице.

Чего это НЕ даёт, и врать себе тут не надо: всё, что умеет отправить браузер,
умеет отправить и `curl` на тот же `/api/graphql`. Прокси прячет адрес и
добавляет слой — он не делает публичное API приватным. Поэтому есть allowlist,
лимиты и авторизация на бэкенде.

### Цена: подписки через такую схему не работают

Route Handler — это запрос-ответ, а не долгоживущий сокет. Нужны
GraphQL-subscriptions — придётся либо выставить наружу WS-эндпоинт бэкенда
(и тогда прятать его уже незачем), либо взять SSE/поллинг.

**Для публичных проектов на массовую аудиторию размен обычно верный**, потому
что подписки там нужны редко. Но выбирать его надо осознанно и заранее — а не
после того, как половина фич завязана на live-обновления.

## Allowlist операций

`src/lib/graphql/allowlist.ts` пропускает **только** документы из
`src/lib/graphql/operations.ts`. Без него `/api/graphql` — открытый прокси:
любой шлёт через него произвольный GraphQL, а прокси заботливо подставляет
service-token. Интроспекция схемы отклоняется тоже.

Цена: новую операцию надо добавить в `operations.ts`. Ловится на первом клике.

## Типы из схемы

```bash
pnpm codegen         # при поднятом бэкенде — перегенерировать
pnpm codegen:check   # для CI: упасть, если сгенерированное устарело
```

Схема читается по HTTP **с работающего сервера**: источник правды — сервер,
а не файл, который забыли обновить. Сгенерированное **коммитится**, чтобы
сборка фронта не зависела от того, поднят ли сейчас бэкенд, — но руками
не правится, следующий запуск перезапишет.

Главное, что это даёт: **тип выводится из твоего запроса**, а не из схемы
целиком. Запросил три поля — в типе три поля; обратился к четвёртому —
ошибка компиляции, а не `undefined` в проде. Переменные типизируются тоже,
поэтому `direction: "Desc"` превращается в `SortDirectionEnum.Desc`
и опечатка не доезжает до сервера.

Тот же `operations.ts` кормит и allowlist BFF: одно объявление — один ответ
на вопрос, что приложение умеет спрашивать.

⚠️ **Забыл перегенерировать — типы уверенно врут.** Это хуже, чем не иметь
типов: на них полагаются. Отсюда `codegen:check` в CI.

## Браузерные тесты (Playwright)

```bash
pnpm e2e            # --headed и с паузой: прогон видно глазами
pnpm e2e:headless   # как в CI
pnpm e2e:report     # отчёт последнего прогона
```

Playwright сам поднимает фронт (`webServer` в конфиге). Бэкенд и базы должны
быть подняты отдельно: `cd ../kit-backend && pnpm db:up && pnpm local`.

Три спеки в `e2e/`, и третья — та, ради которой браузерный тест тут и появился:

| Спека | Что проверяет и почему именно браузером |
|---|---|
| страница открывается | что серверный компонент, Apollo и BFF собрались в рабочую страницу |
| фильтр меняет выдачу | что фильтр не только нарисовался, но и **доехал до запроса**: сверяется тело ушедшего GraphQL-запроса |
| браузер не ходит в бэкенд напрямую | обещание топологии: адреса бэкенда нет ни в бандле, ни в сети клиента. Проверяется единственным возможным способом — списком хостов, к которым реально обращалась страница |

### Что тут стоит подсмотреть

- **`attachDiagnostics`** — печатает ошибки страницы, консоли и GraphQL-ответы
  с `errors`. Без него упавший прогон говорит «строка не появилась», а сервер
  в этот момент отвечал с причиной.
- **`waitForOperation`** — ждать именованную операцию, а не `waitForTimeout`.
  Ожидание по времени — самый частый источник флаков.
- **Локаторы по роли и тексту**, а не по CSS-классу: класс меняется при первом
  редизайне, и тест падает на том, что ничего не сломалось.
- **`expect(statuses.length).toBeGreaterThan(0)`** в спеке фильтра — не
  формальность. Без этой строки тест был ложно-зелёным: на пустой выдаче цикл
  проверок не выполнялся ни разу. Поймано фальсификацией.

⚠️ **Зелёный тест ничего не значит, пока не показано, что он умеет падать.**
Сломай проверяемое и убедись, что покраснело: тридцать секунд, и это
единственный способ отличить тест от его имитации.
